# 10-02: Implement Latest-Change-Wins Synchronization

## Objective

Make offline sync deterministic: when queued offline edits conflict with server-side changes, the newest change wins and all clients converge on the server result.

## Implementation Tasks

1. Add a server sync endpoint for queued task mutations.
2. Define a mutation envelope with `clientMutationId`, operation type, target entity, target id if known, payload, client timestamp, and base/server timestamp where available.
3. Persist applied mutation ids or equivalent idempotency metadata so replayed mutations are not applied twice.
4. Apply queued mutations in timestamp order and implement latest-change-wins for task fields, archive/delete, completion, contexts, and notes according to MVP scope.
5. Return structured per-mutation results: applied, ignored as stale, duplicate, failed validation, or retryable failure.
6. Refresh server task data after sync and update the IndexedDB cache with the canonical response.
7. Handle locally-created temporary ids by mapping them to server ids and updating queued follow-up mutations.
8. Add calm Russian sync messages for stale/ignored updates without interrupting normal task work.

## Acceptance Criteria

- Two edits to the same task resolve so the newest timestamp wins.
- A replayed mutation does not duplicate tasks, notes, or status changes.
- A locally-created task can be edited again before reconnect, then sync as one coherent server task.
- Archive/delete versus later edit follows the latest-change-wins rule.
- After sync, cached task data matches the server response.
- Invalid queued mutations are surfaced as needing attention and do not block later valid mutations forever.

## Verification

- Add unit tests for conflict ordering, duplicate mutation handling, temp-id mapping, and stale mutation results.
- Add API tests for task create/update/archive conflict scenarios.
- Add a browser test for two-device-style conflict behavior using mocked or staged timestamps.
- Run `npm run typecheck`.
